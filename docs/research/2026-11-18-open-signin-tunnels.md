# OPEN-SIGNIN: free ways to reach Bunny from outside the home network over HTTPS

Researcher, 2026-11-18. Official docs and repos only; nothing installed or run. Doc pages were read through a summarising fetch tool; re-read the cited page before building on a number.
Task (from the Chief of Staff, owner's decision 2026-11-18, wishlist at f0d804a): anyone with Bunny's address and passcode can sign in from outside the home network too; HTTPS required over the internet; a free option the owner turns on in Settings, not a router port forward; free only (R4: "if the free tier died tomorrow, would this stop working?").

## What Bunny does today (origin/main e9e84fa, read-only)

- A second server listens on the PC's LAN address only, off by default and off after a restart. [src/server/remoteAccess.js:1-12](../../src/server/remoteAccess.js)
- Host header must equal the LAN `address:port` exactly and Origin must equal `http://` + host; anything else gets 403. [src/server/app.js:3517-3523](../../src/server/app.js) . **Behind a tunnel the Host is the tunnel's name and the origin is `https://`, so both checks must change, and they are a security control (Security's call).**
- Wrong-passcode lockout and the 30-per-10-minutes flood limit are keyed on `req.socket.remoteAddress`. [src/server/app.js:3519](../../src/server/app.js) . **Behind a tunnel every visitor arrives from `127.0.0.1`, so per-device lockout turns into one shared bucket (one attacker locks everyone out, or the limit never bites per attacker) unless Bunny reads the visitor address from a header that only the tunnel can set.**
- The session cookie is `HttpOnly; SameSite=Strict`, with no `Secure` flag. [src/server/remoteAccess.js:303](../../src/server/remoteAccess.js) . Over HTTPS it should gain `Secure`.
- Passcode: 12+ characters chosen, or a generated 20-character one (100 bits), scrypt-hashed; 5 wrong tries make a device wait. [src/server/remoteAccess.js:14-29](../../src/server/remoteAccess.js). Over the open internet, brute-force of a short chosen passcode is the main risk; a minimum of 12 characters is thin for an internet-facing sign-in.
- Chat streams over `text/event-stream` (SSE). [src/server/app.js:1922](../../src/server/app.js), [src/server/app.js:3348](../../src/server/app.js). Any path that blocks SSE breaks live replies.

## Recommendation

1. **Tailscale Funnel is the best fit** for "anyone with the address and passcode": no account for visitors, a stable HTTPS address, TLS ends on the owner's PC so the relay cannot read chats and passcodes, and a free personal plan. Costs: the owner needs a Tailscale account and must turn on HTTPS and Funnel once in Tailscale's admin console; Bunny can only drive the `tailscale` command, not install or sign it in; the hostname appears in public certificate logs; Funnel is beta and the free plan is for non-commercial use. R4 verdict: if Funnel left the free plan, the feature stops, so Settings should say "works while Tailscale offers it free" and Bunny's own LAN mode must keep working without it.
2. **Cloudflare quick tunnel as the no-account fallback** only if SSE works through it, which its own page says it does not. So today it would break live replies: do not ship it as is.
3. **Cloudflare named tunnel** only for an owner who already owns a domain; not a default.
4. **ngrok free**: reject (monthly quotas fail R4; interstitial page; account).
5. **Self-signed + port forward**: reject (the owner ruled out a router port; browser warnings; the installed web app likely fails).
6. Offer **"bring your own HTTPS address"** as an advanced field (any reverse proxy or tunnel the owner already runs), so Bunny does not need to bundle a vendor's tool at all.

## What must change in Bunny for any tunnel (for Security and Builder)

- Accept a configured public host (the tunnel's name) in the Host and Origin checks, over `https://`, and no other. A tunnel makes the Host header untrusted unless Bunny pins the exact name.
- Read the visitor's address from a header only a trusted local tunnel can set (for example `Cf-Connecting-Ip` for Cloudflare; Tailscale Funnel's equivalent header: UNKNOWN, not found on the pages I read), and accept it only for connections from `127.0.0.1`; otherwise keep `remoteAddress`. Without this, lockouts and the flood limit stop working per device.
- Add `Secure` to the cookie when served over HTTPS.
- Raise the bar for the passcode when internet-facing (generated 20 characters by default, longer minimum for a chosen one), keep the action log, and consider an off switch with a time limit ("open for 8 hours").
- Keep it off by default and off after restart, as the LAN mode is now.
