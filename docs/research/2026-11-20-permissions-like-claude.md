## What Bunny has today, for the other column

From the README on main: four modes (Manual asks before every edit, command or click; Accept edits; Auto works on its own but still asks for new tools, schedules that change things, local connectors and email; Plan only looks); rules by command or path, global or per folder, effects Deny, Ask, Allow with **Deny beating Ask beating Allow**; Plan stays read-only whatever a rule says; Bunny's own secrets and data folder protected; important settings change only from Bunny's own window. Engines in v0.1.14 are judged by the same functions. The README states the rules are "a guard rail ... not a sandbox".

## 2. Rule syntax, scopes, and how an approval is remembered

| | **Claude Code** | **Codex** | **OpenCode** |
|---|---|---|---|
| **Syntax** | `Tool` or `Tool(specifier)` in `allow`, `ask`, `deny`, e.g. `Bash(npm run *)`, `WebFetch(domain:example.com)`, `Edit`/`Read` path patterns, MCP tool names with wildcards, `Agent` rules. Wildcards `*`. | Two layers. (a) Command rules in `.rules` files in Starlark: `prefix_rule(pattern=["gh","pr","view"], decision="prompt", justification=..., match=[...], not_match=[...])` with inline tests; **decision** `allow`, `prompt`, `forbidden`. (b) Permission profiles in TOML (`[permissions.<name>]`, filesystem, network domain rules, `deny` reads by path or glob). | `permission` (V1) or `permissions` (V2) config: per action (`read`, `edit`, `bash`, `webfetch`, `websearch`, `task`, `skill`, `external_directory`, ...) a value or an object of patterns; V2 uses a list of `{action, resource, effect}`. |
| **Who wins** | **Deny, then ask, then allow; the first match in that order decides.** An allow cannot carve an exception out of a deny, from any scope. | **Most restrictive wins** (`forbidden` > `prompt` > `allow`). | **Last matching rule wins** (V1 and V2); no match means ask. |
| **Compound commands** | Rules are checked per sub-command; documented limits ("Bash rule limits") for forms the rules don't match. | A linear chain of plain words joined by `&&`, `||`, `;`, `|` is split (tree-sitter) and each part judged, most restrictive wins; anything with redirects, substitutions, variables, globs or control flow is **not split** and judged as one `bash -lc "<script>"`. | Shell commands are parsed by a built-in scanner; "compound commands can produce several" resources (V2 text). |
| **Scopes** | User `~/.claude/settings.json`; shared project `.claude/settings.json` (committed); project local `.claude/settings.local.json` (git-ignored); managed policy above all. Project allow rules apply only after the **workspace trust** dialog; deny and ask rules do not need it. | User `~/.codex/config.toml`; project `.codex/config.toml` and `.codex/rules/` (**loaded only when the project is trusted**); system `/etc/codex/config.toml`; managed `requirements.toml`; Team Config layers. | Global `~/.config/opencode/`, project `opencode.json`, `OPENCODE_CONFIG`, inline `OPENCODE_CONFIG_CONTENT`/`OPENCODE_PERMISSION`, managed; merged, later overrides earlier. Per-agent permissions override. |
| **How an approval is remembered** | Prompt options: Yes (once); "Yes, and don't ask again for: `npm test *`"; sometimes "allow for the rest of the session"; "Yes, and switch to auto mode". A saved Bash or WebFetch rule goes to `.claude/settings.local.json` **at the git root, resolved through worktrees**, for future sessions in that repository; file-edit approvals last until the session ends; web search is saved per repository. A prompt that cannot show everything an "always" would allow offers only a one-time approval. | Adding a command to the allow list in the TUI writes `~/.codex/rules/default.rules` (the **user** layer, every project). Smart approvals may **propose** a `prefix_rule` during an escalation request; the person must review it. Session-only vs saved wording of the TUI prompt: UNKNOWN (not read). | `once`; `always` ("approve future requests matching the suggested patterns", V1: "for the rest of the current OpenCode session"; V2: saved as project-scoped allow rules that never override a deny); `reject` (rejects every other pending request in that session too). |
| **Per-chat or per-folder** | Per repository via the local settings file; per session for edits; Desktop remembers the chosen mode per folder. | Per user (rules), per project (project layer, trusted), per session (mode). | Per project and per session. |

## 3. Auto or classifier modes

| | **Claude Code auto mode** | **Codex Auto-review ("Approve for me")** | **OpenCode `--auto`** |
|---|---|---|---|
| **What it is** | A **separate classifier model** reviews actions instead of the person. | A **separate reviewer agent** reviews approval requests (`approvals_reviewer = "auto_review"`). | No judge: approves whatever would ask. "Explicit deny rules are still enforced." |
| **What is judged** | Decision order, first match wins: (1) allow, ask, deny rules resolve at once (except protected-path writes, critical `rm`, user-interaction tools, network paths, which go on to the classifier or the person); (2) **read-only actions and file edits inside the working directory are auto-approved without the classifier**; (3) **everything else goes to the classifier**. On entering auto mode, broad allow rules that grant arbitrary code execution (`Bash(*)`, `python*`, `Agent`, `Monitor`) are **dropped**. | Only requests that already need approval: shell calls asking for escalated sandbox permissions, commands matching a `prompt` rule, network requests needing approval, edits outside writable roots, MCP or app calls that need approval. "Actions that already have permission to run proceed without review." Computer Use app-level prompts go to the person. | n/a |
| **What it sees** | User messages, tool calls other than read-only lookups, and CLAUDE.md. **Tool results are stripped**, so hostile file or web content cannot steer it. A server-side check can replace the classifier calls on a direct API connection. | The proposed action; the reviewer returns a rationale. | n/a |
| **Blocked by default** | Downloading and running code (`curl | bash`), sending sensitive data out, production deploys, mass deletion, IAM changes, force push, `git reset --hard` and similar, deleting pre-existing files irreversibly, merging unapproved PRs, disabling CI, and more. | Sending private data or secrets to untrusted destinations, probing for credentials, broad security weakening, destructive actions with irreversible damage (list continues in the page). | n/a |
| **Person's words count** | "Boundaries you state in conversation" (don't push) are read as blocks; "approvals you state" can clear a block, usually for one action. A boundary lost to context compaction is lost: a deny rule is the hard guarantee. | UNKNOWN. | n/a |
| **When it falls back** | Block 3 times in a row or 20 in total: auto mode pauses and prompting resumes; non-interactive runs just keep working without the blocked action. No verdict means the action is denied. | A denial tells the agent to "find a materially safer path or stop and ask the user". | n/a |
| **Cost** | Classifier calls count toward usage on API and Enterprise accounts; adds a round trip. Needs a supported Claude model. | A reviewer model call per eligible request; UNKNOWN cost. | none |

|---|---|---|---|

## What makes Claude and Codex feel "fluid" (the owner's complaint) — facts from the pages, not a design

The sources show five separate reasons they stop less often than a plain Manual mode. Each is documented above; a design is for Design and Security to decide.

1. **They allow the safe middle by default.** Reads inside the workspace never ask (Claude, Codex); Claude has a built-in set of read-only commands that never ask and pre-approved documentation domains; edits and common file commands inside the folder are one mode away (`acceptEdits`).
2. **Codex lets the sandbox, not the prompt, carry the safety** for commands inside the workspace, including a native Windows sandbox, so `workspace-write` + `on-request` is already the default "Auto".
3. **A second model reviews the rest** (Claude's classifier, Codex's reviewer) instead of the person, but only for actions that would otherwise prompt, with tool results hidden from the reviewer in Claude's case.
4. **A saved approval is remembered where it will be needed**: Claude's "don't ask again" saves a rule per repository (through worktrees); Codex writes the user rule file; OpenCode saves per project in V2.
5. **They treat a few things as always needing the person**, whatever the mode: explicit ask rules, user-interaction tools, critical deletions, protected configuration paths (Claude); escalation, network, destructive tools (Codex). Computer use is separate: off by default, enabled once in Settings, then approved per app per session with fixed tiers.

## How each compares with Bunny's current model (facts, then a gap list)

- **Rule order.** Claude deny-ask-allow equals Bunny's; Codex "most restrictive wins" equals it in effect for rules that all apply; OpenCode "last match wins" differs, so an imported OpenCode list could invert a deny (see my earlier note on engine rules).
- **Rule vocabulary.** Bunny's rules are command patterns and path patterns with edits or reads; Claude's are per tool (Bash, Read, Edit, WebFetch, MCP, Agent) with specifiers; Codex splits command rules from filesystem/network profiles; OpenCode keys by action. Bunny has no rule for **a network domain**, **a tool name** (an MCP tool, the browser, desktop control) or **an agent**: all three rivals can write those.
- **Modes.** Bunny's four map as Manual to `default`/`on-request`, Accept edits to `acceptEdits`, Plan to `plan`/`read-only`. Bunny's Auto has **no reviewer**: it goes ahead except for a short fixed list; Claude's and Codex's Auto put a second model in front of the risky remainder. No mode like `dontAsk` (deny anything that would prompt) or a bypass mode with documented always-ask exceptions exists in the README.
- **Protected paths.** Bunny protects its own data folder and secrets. Claude protects repository and tool configuration (`.git`, `.vscode`, shell profiles, `.mcp.json`, CI and hook configs); Codex protects `.git`, `.agents`, `.codex`, `.aws`. The README does not say whether Bunny's file tools treat the project's own `.git` or shell-profile files as protected: UNKNOWN.
- **Remembered approvals.** Bunny's rules are saved by the person in Settings; whether a prompt offers "don't ask again for this command" that writes a rule is UNKNOWN from the README (the v0.1.14 plan mentions "Allow for this chat" gated on Security's EN-9).
- **Sandbox.** None for Bunny (stated in the README); none for Claude on Windows; **Codex has one**. This is where Codex's smoothness comes from, and the only one of the three that could be copied in kind, by Security's call.
- **Tool discovery.** Claude defers MCP tool definitions and finds them by search; Bunny's agent-flow work (v0.1.16 workstream 1) is the owner's complaint. The owner's example "it should know whether it has those tools or not; if not, look for them" corresponds in the sources to Claude's tool search plus the Settings switch for computer use, and to Codex's `request_permissions` tool.
