# 0.1.6 plan: fix every gap left after 0.1.5

> **Version numbers (2026-11-16, Chief of Staff):** the W0-4 hotfix ships as **v0.1.6**, not 0.1.5.1, because the updater needs a
> three-part version. The release this plan builds toward is therefore **v0.1.7**. Wherever this file says "0.1.6 release", read 0.1.7.
>
> **One release for everything (owner, 2026-11-16):** "now we will push all pieces together, after fixing all gaps." No interim releases: every
> piece is built, reviewed and signed on its own branch, then assembled once into v0.1.7, gated on a quiet machine, and pushed to main only on
> the owner's "push to main" and published only on the owner's "release v0.1.7" in Release Ops.

Every open row from the morning report is listed here once, with the session that does it, its risk, the files it touches,
and the test that proves it is done. Nothing in this plan is "done" until the test named in its row passes, and the deciding
session re-checks it from the diff (O1).

## How the work runs

- **One writer per file.** Builder writes product code. Only one lane edits the shared hot file (`src/server/app.js`) at a time.
  Wave 2 is split in two so the tool work (`workspace.js`) and T-4 can run side by side without touching the same lines.
- **Review lane, unchanged from 0.1.5.** QA walks it, Tech Lead reviews the diff, Security signs anything MEDIUM or above that
  touches permissions, files outside the workspace, the network or secrets, and Design approves anything a person sees (O3,
  drawn before it is built).
- **HIGH rows wait for the owner's go** (AGENTS.md risk levels). They are marked **GO NEEDED**. Everything else starts now,
  under the standing delegation.
- **Gate per piece, one session at a time**, until W4-1 gives each worktree its own test port. After W4-1, gates can run in parallel.
- **Release:** one 0.1.6 release at the end of Wave 3, plus a 0.1.6.x for anything from Wave 4 and 5 that lands later. The owner types
  "release v0.1.6" in Release Ops, as for 0.1.5.
