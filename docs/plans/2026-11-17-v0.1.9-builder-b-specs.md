## W6-12 Long Code tasks keep a task list (LOW)

**Today.** `update_tasks` exists (`src/server/agentTools.js:257` `cleanTasks`, at most 20 steps); the list is kept per
reply only: `let currentTasks = []` at `src/server/app.js:1804`, set at `:2588-2592`, saved with the reply
(`src/server/sessions.js:242-245`). The prompt asks for a list on long jobs (`app.js:1850`) and the end-of-reply
nudge only fires when the reply ends with a permission question (`app.js:2818-2830`). So the next message starts
with no list: the model forgets steps the person never saw done.

**Build.**
1. At the start of a Code reply, seed `currentTasks` from the newest saved assistant message that has `tasks`
   **if it still has an open step** (same lookup the UI uses, `src/ui/chat.js:1114`). Tell the model in the system
   text: "Your task list from earlier (N of M done): ...; keep it current with update_tasks." Not in Chat mode,
   not for helpers (`agentScope.getStore()`), not in Plan mode (Plan may read it, the line says "plan only").
2. Raise the cap to 40 steps in `cleanTasks` and in `sessions.js:244` (both places, same number).
3. `onReplyEnd` (`app.js:2818`): when the list has open steps and the reply ends **without** a question to the
   person (no `ask_user` card, text not ending in "?"), nudge once per reply with the open steps named
   (count against the existing `permissionNudges` limit of 3). A reply that says plainly it is blocked or finished
   is left alone (reuse the W6-3b wording test).
4. When every step is done, the next reply starts with no seeded list.

**Done when** (unit tests in `test/w6-12-tasks.test.js`, scripted model):
- a second message in a chat whose last list has 2 open steps: the model's first request carries the list line,
  and the reply's saved `tasks` keep the earlier steps;
- an all-done list is not seeded; Chat mode and a helper are not seeded;
- a reply that stops with open steps and no question gets exactly one nudge; one that ends with "?" or an
  `ask_user` card gets none; 41 steps save 40.
- QA's walk: Tasks pane shows the carried list after a reload.

## W6-24 Sites that refuse framing in the browser panel (MEDIUM)

**Today.** Each tab is an `<iframe sandbox=...>` (`src/ui/browser-pane.js:142-150`). In the desktop app,
`electron/main.js:258-270` already drops `X-Frame-Options` and CSP `frame-ancestors` for sub-frames, so most
"refused to connect" pages load. What still fails: (a) sites that frame-bust in script or check `window.top`;
(b) sign-ins: third-party cookies in a frame are `SameSite`-blocked, so Google, Microsoft and many shops cannot
log in; (c) `checkBlocked` (`browser-pane.js:183-191`) only sees a blank same-origin frame; Chromium's error page
is cross-origin, so the "this site refuses" hint never shows for a real refusal; (d) the panel uses
`session.defaultSession`, the same cookie jar as Bunny's own pages.

**Build (desktop only; the web build keeps iframes and shows the hint).**
1. A tab can be an Electron `WebContentsView` laid over the panel's rectangle: renderer sends the rectangle
   (ResizeObserver on the tab host, plus show/hide when the pane or tab changes) over a new IPC
   `browser:view` (same `isOwn` check as `browser:act`, `main.js:212`). The view uses its own partition
   `persist:bunny-browser`, `sandbox: true`, `contextIsolation: true`, no preload, `nodeIntegration: false`;
   `setWindowOpenHandler` opens new windows as a new tab, never a new app window; `will-navigate` allows
   http(s) only.
2. When to use it: every new tab in the desktop app (simplest, one code path), **or** at least a tab whose
   frame failed. Tech Lead prefers every tab: then (b) and (d) are fixed too. Builder decides and writes it in
   the commit.
3. `controlFrame` (`electron/browserAgent.js:144-175`) gets a twin for views: `read/click/type/scroll` run the
   same `pageScript` with `view.webContents.executeJavaScript`, screenshot is `view.webContents.capturePage()`.
   Names `bunny-tab-<n>` stay the address; main keeps the map tab name -> view.
4. Back, forward, reload, address bar and the dev-server card (`browser-pane.js:195`) drive the view through
   the same IPC.
5. Fix (c): detect failure with `did-fail-load` on the view (and for iframes keep today's hint).
6. Plan mode and `BROWSER_TOOL_RISK` (`src/server/browserTools.js:14`) are unchanged: same tools, same risks.

**Done when:** a site that frame-busts (local test page that does `if (top !== self) top.location = ...`) and a
page that sets a `SameSite=None` sign-in cookie load and keep the cookie in the view; `browser_read`, `click`,
`type`, `screenshot` work on a view tab (unit test with a fake contents object for the IPC routing, plus the
real window walk by QA); a `window.open` from the page becomes a tab; a `file:` or `javascript:` navigation is
refused; the view hides when the pane closes or another chat opens (no view floating over Settings); the panel's
cookies are not visible to Bunny's own origin (and the reverse). Security reads the partition and IPC.

## W6-6 Install a tool from any GitHub repo (HIGH: runs third-party code; Security signs)

**Today.** `install_plugin` reads a repo through the GitHub API and brings in skills and **remote** connectors
only; scripts are skipped, never run (`src/server/pluginImport.js:1-11, 33`). A local connector from the chat
must be one of `npx, node, uvx, python, python3, docker` with plain-string args (`src/server/mcpLocal.js:23, 33-44`),
is `build` risk (`app.js:2639-2642`). The GitHub clone helper is at `src/server/github.js:250`.

**Build.**
1. New agent tool `install_from_github { repo, kind?: 'mcp' | 'cli' }`, risk `build` (asks in Manual and Accept
   edits; in Auto it runs, like `add_connector` with a command today; Plan refuses). Helpers never get it (add to
   `HELPER_NEVER`, `app.js:2113`). The card shows: repo, its default-branch commit sha, stars and last push, the
   exact install command, and "This runs code from the internet on this computer".
2. Clone with `git clone --depth 1` (no token unless the repo is private and GitHub is connected) into
   `<data folder>\tools\<owner>-<repo>-<sha7>\`, never into the chat folder. Pin the sha shown on the card: if the
   default branch moved between card and clone, stop and show the card again.
3. Read `README*`, `package.json`, `pyproject.toml`, `.mcp.json` / `mcp.json` to pick the install: `npm ci`
   (`npm install` only when there is no lock file, and say so) or `uv pip install` / `pip install -e .` in a
   venv inside the tool folder. **`--ignore-scripts` for npm unless the person ticks "Allow install scripts"** on
   the card. No `sudo`, no global installs, no PATH edits, nothing outside the tool folder.
4. Register: for `kind: 'mcp'`, a local connector `{ command: 'node' | 'python', args: [<entry inside the tool folder>] }`
   through the existing `mcp.add` (`mcpStore.js:42`) so the existing start, timeout and sign-out code is reused;
   for `kind: 'cli'`, a custom tool entry that runs the binary from the tool folder with `run_command`-equivalent
   checks (cwd = chat folder, the person's rules apply). The entry records `source: { repo, sha }`.
5. Uninstall (Customize, and `appTools.uninstall`) removes the connector or tool **and** the tool folder (path
   re-checked to be inside `<data folder>\tools`), and signs any connector out (Security's W3-6 note).
6. Updates: none automatic. "Check for a newer version" shows the new sha and the card again.

**Done when** (`test/w6-6-install.test.js`, against a local bare repo served by the test, no network):
install of an invented MCP repo registers a connector whose tool answers; the sha on the card equals the installed
sha, and a moved branch stops the install; `npm ci` runs with `--ignore-scripts` unless allowed (assert the argv);
a repo whose `package.json` has a `postinstall` that writes a marker file outside the tool folder leaves no
marker by default; Plan mode refuses; a helper does not see the tool; uninstall removes connector and folder, and
a tampered saved path outside `tools\` is refused; an old profile with no `tools` folder starts fine.
Security reviews the card wording, `--ignore-scripts` default, and the uninstall path check before merge.
