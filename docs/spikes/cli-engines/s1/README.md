## Verdict: FULL MODE, with a required second layer (a condition, not a failure)
- The hook sees every tool and a deny stops it, and the project and personal configs are not loaded: S1 (a), (b), (d) pass.
- S1 (c) does **not** pass as the spec words it: the hook alone fails **open** for a crash, exit 1, bad output, timeout, kill and missing runtime. The adapter must therefore (1) wrap the hook so everything it can catch ends in a printed deny, **and** (2) run Claude Code with `--permission-prompts none` (or `--permission-prompt-tool` answering deny) and no allow rules at all, so a hook that dies leaves the engine's own permission system, which denies writes, commands, fetches, MCP and outside-folder reads; **and** (3) write `permissions.deny` for Bunny's protected paths into Bunny's own settings, because a read **inside** the workspace of a protected file is auto-allowed when the hook fails open.
- Security should decide whether that residual is acceptable: when the hook dies, the engine can still read workspace files that Bunny's rules would have asked about and that no deny rule covers.
- Found, for Tech Lead: this build has `--restricted` (removes command tools and WebFetch, ignores user/project/local settings files, confines file tools to the working folders) and `--permission-prompts host|none`; both look useful for restricted mode and for the fail-closed layer, and neither is in the spec's facts.
- Not tested here: a hook timeout longer than an Ask card's wait (CE-1.2); a real bridge; interactive (non-`-p`) mode; stream-json input.

## Addendum: `--restricted` (asked for by Tech Lead via the Chief of Staff)
Exact `--help` text: `evidence/restricted-help.txt`. Runs: `evidence/r-restricted-*.txt`.
- **Tools removed.** The `system/init` tools list under `--restricted` has no Bash, PowerShell or WebFetch (a model that asks for them gets "No such tool available: Bash. Bash is disabled for this session, in subagents as well as here."). **Still offered:** Edit, Write, Read, Glob, Grep, NotebookEdit, Task (the subagent tool; the hook sees it as `Agent`), ListAgents, SendMessage, Skill, WebSearch, ToolSearch, Cron*, EnterWorktree/ExitWorktree, TaskCreate/Get/List/Update/Stop, ScheduleWakeup, ReportFindings, and **every MCP tool** from the `--mcp-config` given (`--strict-mcp-config` only limits MCP to that config; to have none, pass none). No tool named Monitor was in the list. So under CE-8.3 the adapter must still pass no MCP config and judge WebSearch, Agent/subagents, Skill and the Cron/worktree tools through the hook (or hide them with `--disallowedTools`, not tried).
- **Combines with the rest.** With `--restricted --settings <bunny file> --setting-sources user` and `CLAUDE_CONFIG_DIR`, the hook still fired (7 calls seen, subagent calls with agent ids), the project's and the fake home's allow-all configs fired 0 times, and a hook deny still denied (`r-restricted-hook-deny`).
- **Canary under `--restricted`.** With the hook allowing everything, a Read of `canary.txt` outside the folder did not return its content (`r-restricted-canary-allow`; the string never reached the endpoint or stdout): file tools are confined to the working folders by the engine itself. With the hook killed and `--permission-prompts none`, the canary also stayed unread (`r-restricted-killed`), while a read of `secret.txt` inside the folder ran, as before.
- **Does a command still run when the model asks?** No: with the hook allowing everything, scripted Bash and PowerShell calls ran nothing (`bash-ran.txt`, `ps-ran.txt` absent; the model got "disabled for this session"). Checked at the stand-in's request log, not the process list: the commands write a marker file and none appeared; no child shell process was observed because no command tool exists to start one.
- **Note:** under `--restricted` with a hook that allows, Write (acceptEdits) did write a file inside the folder, and the MCP tool ran: `--restricted` is not a no-writes mode; Bunny's hook (or its staged copy) still has to be the judge for writes.
