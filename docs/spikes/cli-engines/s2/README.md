## Verdict: FULL MODE is possible, but only with `approval_policy = "untrusted"`, not the granular policy
- Run Codex with `untrusted` for every run (never `on-request`, never `granular`: with the sandbox active they ask for nothing in the folder). Bunny then receives every command and every file change before it runs, and decline stops each.
- What Bunny sees for a command is its text (a `powershell.exe -Command "..."` line), so it judges it as a `run` step; it cannot see which file a command reads. **A command Bunny allows can read the canary outside the folder; no Codex setting here closes that** (the sandbox does not restrict reads). So full mode's read confinement rests on Bunny's rule for commands (Ask in Ask mode, Deny in Plan), the same as for Bunny's own engine, and the owner's R23 question stays open for full mode.
- **Restricted mode is available and the canary stays closed**, with: `features.shell_tool=false`, `features.unified_exec=false`, `features.view_image=false`, plus apps/plugins/computer_use/image_generation/goals/hooks off and `web_search="disabled"`. The only tools left are `apply_patch` (every change asks, outside-folder paths too), `request_user_input` and `tool_search`.
- Adapter facts for Tech Lead: (1) pass `capabilities.experimentalApi` only if granular is wanted (it is not); (2) rewrite the isolated `config.toml` before each run, because the first run marks the project trusted; (3) turn the plugin/app features off or Codex contacts github.com and chatgpt.com; (4) the model name decides which tools Codex offers; (5) `windows.sandbox="unelevated"` is optional and gives write confinement only.
- Not tested: a real model; `acceptForSession` semantics; Codex hooks; whether a trusted-project `.codex/rules` file can bypass `untrusted` (UNKNOWN, see above); `codex exec` mode; stdin/stream use beyond `app-server`.

## Addendum: CE-1.15, untrusted projects' exec-policy rules (asked for by Security via the Chief of Staff)
**What was shown** (`evidence/m-broken-*.txt`; the rule file is deliberately unparseable, so Codex reports it only if it reads it; `evidence/j-*` and `k-*` for the asks):
- **Control, the rule file is read when it can be:** a broken `rules\default.rules` in the isolated `CODEX_HOME` is reported at start ("Error parsing rules; custom rules not applied. failed to parse rules file ...\codex-home\rules\default.rules: starlark error ...", `m-broken-home-control`).
- **Trusted project:** with the isolated `config.toml` saying `[projects.'<project>'] trust_level = "trusted"`, the project's `.codex\rules\default.rules` is read: the same parse error is reported for `proj\.codex\rules\default.rules` (`m-broken-project-trusted`).
- **Untrusted project:** with `config.toml` rewritten to `trust_level = "untrusted"` for the project, **no error and no mention**: the project's rule file is not read (`m-broken-project-untrusted`). Same with no entry at all on the first thread (`m-broken-project-no-config`).
- **The ask is not suppressed:** under `approval_policy = "untrusted"` a project `allow` rule (and a `forbidden` rule) in a trusted project and in an untrusted one all left the command asking (`j-untrusted-{trusted,untrusted}-{allow,forbidden}`: 2 `item/commandExecution/requestApproval` each, `ran.txt` absent after decline). Honest limit: this shows nothing about the rule, because a rule written for the PowerShell path does **not** change the ask even in the **trusted** case or in the home-level control (`j-control-home-forbidden`, `k-nosandbox-onrequest-home-allow`: still asked). `codex execpolicy check` accepts the same rule text (`{"decision":"allow"}`), so the syntax is right; Codex wraps these commands in `powershell.exe -Command "<line>"` and appears not to apply prefix rules to that wrapper on Windows. The file-is-read proof above is therefore the evidence that matters for CE-1.15: **an untrusted project's rules are not loaded.**
- `thread/start` with a writable sandbox does **not** overwrite an existing `untrusted` entry (`config.toml` after the run still says `untrusted`, in the `config.toml` line of `m-broken-project-untrusted`); with no entry it adds `trusted`, so Bunny's per-run `config.toml` rewrite must write the `untrusted` entry, not just omit it.
