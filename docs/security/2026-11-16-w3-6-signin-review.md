# W3-6 sign-in connectors (MCP OAuth) — Security review

Date: 2026-11-16 · Session: Security · Reviewed: `claude/builder-a-w3-6-final` @ `1a1c364` (with W5-7 `400946b` merged): `src/server/mcpOAuth.js`, `connectorSignIn.js`, the `requestGuard.js` callback exception, `mcp.js` auth hook, the route and chat changes in `app.js`.
Method: read all of `mcpOAuth.js` and `connectorSignIn.js` and the diffs around them; Builder's tests run on a scratch checkout (43 of 43 pass: `mcp-oauth` 31, `mcp-signin-routes` 12); a probe of the engine with a stub provider (`docs/security/w3-6-probe/oa.mjs`). Nothing run against a real provider; the e2e spec and the real browser hand-off were not run.

## Verdict: **PASS with conditions** (two verified follow-ups, neither stops 0.1.8 if fixed in the same release)

## What holds (read, and covered by Builder's tests)
- **Flow.** Discovery by RFC 9728 and 8414 (three metadata locations), a public client by registration (RFC 7591) or a pasted client id, authorization code with **PKCE S256** (48-byte verifier, refused when the server lists PKCE but not S256) and the resource indicator, `state` of 32 random bytes, one use (deleted before the exchange starts, "whatever happens next"), 5-minute life, at most 8 pending, `iss` checked when sent (RFC 9207), the provider's error text never repeated except a plain `[a-z_]` code.
- **The callback exception.** `requestGuard` lets exactly one path through without the page token: `GET /api/connectors/oauth/callback`, and only for a state that is pending. A program that does not know the state is refused 403 `request.badState`. A program that learns the state still cannot finish a sign-in with a code of its own: the exchange needs the verifier that only the server holds. The page it answers has no script, `default-src 'none'`, `no-store`, `no-referrer`, and escapes its text; messages shown are Bunny's own sentences, not the provider's.
- **Where requests go.** Every provider address must be https (http only for this PC), no password in the address, redirects refused (`redirect: 'error'`), answers capped at 1 MB and 15 s. A connector out on the internet may not point any discovered address (issuer, authorization, token, registration, revocation, userinfo, resource-metadata) at this computer or the local network (loopback in every spelling the URL parser leaves, `0.0.0.0`, 10/8, 172.16/12, 192.168/16, 169.254/16, `::1`, `fe80`, `fc/fd`, `::ffff:`); the connector's token address must be https for it to be used.
- **Secrets.** Tokens only in the secret store (`mcp:<id>:oauth`); `status` returns signed-in, account name and expiry, never a token; errors and messages carry no token; the window cannot read one. Refresh is single-flight and a rotated refresh token replaces the old; `invalid_grant` removes the token and asks the person to sign in again.
- **Routes.** Start and sign-out are window-only (route table, tested); a local connector is refused; a connector removed while the person was away is signed out as soon as the return arrives. Deleting a connector signs out first (5 s cap) and then removes the token whatever the provider said.
- **A 401** is turned into `mcp.needsSignIn`; the raw text never reaches the model or the window; the chat step tells the model not to call the connector again until the person signs in.

## Findings
**W36-1 MEDIUM-LOW (verified): the stored token is not tied to the connector's address.** It is stored under the connector's id, and `authHeader` sends it to whatever URL the connector has now. A connector whose address is edited (`PATCH /api/mcp/:id` takes `url`; window-only, but the person is the one who edits it) keeps the token that was issued for the old address (`resource=`), and my probe shows it sent to `https://elsewhere.example/mcp`. The same edit to `http://…` would send it in clear text. Fix: store the connector's origin with the token; in `authHeader` send nothing (and treat the connector as signed out) unless `new URL(server.url).origin` equals it and the address is https (or loopback); in `mcp.update`, sign out when `url` changes.
**W36-2 LOW-MEDIUM (verified): a refresh that is already running can bring a signed-out token back.** `doRefresh` awaits the provider and then writes the new token. In my probe, sign-out deleted the token, the refresh finished, and `mcp:<id>:oauth` held a live token again: the person is "signed out" but the connector still has access, and the provider was told to revoke the *old* token only. The same happens on deleting a connector during a refresh. Fix: in `doRefresh`, re-read the token before writing and write only if it is still there and still holds the refresh token it started from; have `signOut` wait for `refreshing.get(id)` (or mark the connector as signed out so the late result is dropped, and revoke the new tokens it returns).
**W36-3 LOW, known gap:** the private-network check looks at the host name as written. A name that resolves to a private address (DNS) passes, and a few ranges are not listed (100.64/10, 198.18/15, `::/96`, NAT64, `.local`/`.internal` names). Only a connector the person added themselves can ask for this, over https, with OAuth-shaped bodies; accepted as Builder lists it.
**W36-4 LOW:** a registered client is cached per issuer **and return address**, and the return address contains this launch's port, so each launch registers again and leaves one more `mcp-oauth-client:…` entry in the secret store. Fix: key on the issuer only and re-register when the provider rejects the redirect, or bound the number kept.
**W36-5 LOW:** `GET /api/connectors/:id/oauth` carries the signed-in account name (often an e-mail address) and is open to the page token like the other reads. Fine for the window; mention in the help text that it is shown.

## The revoke-on-sign-out decision
Confirmed as drawn: revoke at the provider (refresh token first, then access token, RFC 7009, public client) on a best-effort basis, **delete the local token whatever happens** (`finally`), and tell the person honestly which of three things happened (revoked / not confirmed / no revoke endpoint). That is the right order: a provider outage must never leave the token here. It needs W36-2 to be true in every case.

## Not done
No real provider, no real browser hand-off (`window.open`) and no e2e spec; the Automation-page list and static-header 401 gaps Builder names were not reviewed; the secret store used in tests is in memory (the real store is the DPAPI one reviewed in the baseline).
