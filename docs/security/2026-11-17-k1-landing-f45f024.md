## K1-5 MEDIUM-LOW (verified; same in the v0.1.7 guard and in the live one): the limits do not bound the time for shapes that start a process per part
A `git push` part costs about 60 ms here (it runs `git rev-parse` to find the branch; a short ref name costs a second lookup): 
| Command | Answer | Time |
|---|---|---|
| 10 × `git push origin claude/x;` | allowed | 0.56 s |
| 50 × | allowed | 3.2 s |
| 100 × | allowed | 6.2 s |
| 150 × then `git push origin main` | refused | **9.1 s** |
| 300 × then `git push origin main` (or then `echo x > AGENTS.md`) | refused | **18.4 s** (19.0 s) |
| 1,999 × (51 KB, under both limits) | allowed | **232 s** |
The hook is configured with `"timeout": 10` (`.claude/settings.json`). QA's premise, which I share, is that a hook cut off by the host does not block the call. Then a command of about 160 harmless pushes followed by the real one runs unchecked, and the guard's answer arrives after the host has stopped waiting. It needs a crafted command, but it is exactly what the new limits were meant to stop, and they do not stop it: the cost is per part by shape, not per character. **Fix (small, no new rule):** (a) read the git branch once per `decide()` and reuse it for every part (the 60 ms becomes microseconds); (b) give `decide()` a deadline (for example 6 s from the start): when it passes, refuse with "too slow to read", checked between parts and before every process start, and give each `execFileSync` a `timeout` of the time left; (c) as a belt, let `main()` run the decision in a child process with `spawnSync(..., { timeout: 8000 })` and treat a timeout as exit 2, so a stuck hook can never be a pass. I accept landing without it because the live guard has the same hole today and arbitrary code (`node -e`) already goes round the guard (accepted since W5-1); the pre-commit and pre-push hooks are the backstop. I do not accept it as "closed": please keep QA's finding open until (a) and (b) are in, and tell QA the 1,999-push shape.
(Measured at idle; under load every figure grows, QA's 21,000-part case took 23–31 s.)

## The `flow-editor.html` note from the automated reviewer: **does not block landing**
`scripts/kit-next/.bootstrap/ui/flow-editor.html` and `bin/flow-ui.mjs` are byte-identical to the plugin's 0.6.0 files (compared). The editor is a local page the Chief of Staff opens with `bootstrap flow`: `flow-ui.mjs` binds to `127.0.0.1` only, needs a per-run random token (in the page URL, then as a header for the API), checks the `Host` header against `127.0.0.1`/`localhost` (blocks DNS rebinding) and caps the POST body. The values the page shows come from `flow.json` and `company.json`, which only the Chief of Staff can change (protected files) and a flow change reaches `main` only with the owner's recorded yes for those exact bytes (the push check). So unescaped values could only be reached by someone who can already edit the flow. Risk accepted. Hygiene, not a landing condition: do not open `bootstrap flow` on a branch whose `flow.json` nobody has read, and tell the plugin's author.
