## S-1 HIGH — local API accepts any caller (no Origin / Host / token check)

**Evidence.** `route()` (`src/server/app.js:433`) goes straight to handling by path and method. There is no check of `Origin`, `Host`, `Sec-Fetch-Site` or a secret token anywhere (`grep` for `origin`, `sec-fetch`, `csrf`, `Access-Control` finds only code that *builds* URLs). `readBody` (`:108`) parses JSON whatever the `Content-Type` is, so a cross-site `fetch(..., {method:'POST', mode:'no-cors', body: JSON.stringify(x)})` (a "simple" `text/plain` request, no preflight) is accepted. The server listens on `127.0.0.1` on a random port (`electron/main.js:50`).

**Why it matters.** Browsers allow a web page to send such requests to `127.0.0.1`; the page cannot read the answer, but the side effects happen. Reachable actions include:
- `POST /api/mcp` with `{command, confirmLocal:true}` (`app.js:806-813`). The "confirm" is a flag the caller sets, not a person's click, so it is not a control. That adds a connector that runs a program: code execution as the owner.
- `PUT /api/settings` (`:575`), `/api/import`, memory writes, session creation, `/api/account/github/token` (`:450`).
- DNS rebinding makes the port guess unnecessary and the responses readable, so chats, memory and settings can be read.
The random port is the only barrier today, and it is a scan away (about 28k ephemeral ports). *Not run: no exploit attempted; the reasoning follows the code.*

**Recommendation (Builder).**
1. Reject any request whose `Host` is not exactly `127.0.0.1:<port>` (stops DNS rebinding).
2. Reject requests that carry an `Origin` other than the app's own, and any with `Sec-Fetch-Site: cross-site` or `same-site`.
3. Generate a random token at start, hand it to the window (preload or first page load), and require it as a header on `/api/*` except the page itself.
4. Make the local-connector confirmation a real prompt owned by the main process, not a request field.
5. Require `Content-Type: application/json` on JSON routes.
Tests: a new e2e case that sends a wrong Host, a foreign Origin and a missing token and expects refusal.
HIGH per AGENTS.md (security controls): needs the owner's go before build.

## S-2 MEDIUM — update integrity depends on one trust root and fails open

**Evidence.**
- `readRelease` (`electron/updater.js:42-47`): `sha512` is `null` when the release has no `latest.yml`; `download` only compares when `release.sha512` is set (`:77`). A release missing that file installs with no integrity check at all.
- The checksum is read from the same GitHub release as the installer, so it detects corruption and a bad CDN, not a tampered release or a takeover of the GitHub account / token that publishes it.
- The installer is not code-signed, so Windows SmartScreen cannot vouch for it and the updater does not check an Authenticode signature before `spawn` (`:122`).
- `size` check is skipped when `release.size` is falsy (`:81`).
- Feed is overridable by `BUNNY_UPDATE_FEED` (`:50`): only reachable by a process that already sets the app's environment; `main.js` allows it when set even unpackaged. Fine for tests; note it.
- Positive: SHA-512 is compared to a base64 digest and the file is deleted on mismatch; updates only run in the installed app; install happens on the person's click or on quit.

**Impact.** Whoever can publish a GitHub release for `AnfalHaider/bunny-ai` ships code to every installed copy within hours. That is the project's one REAL thing, so the account is the crown jewel.

**Recommendations.**
1. Builder: refuse an update with no checksum (fail closed); require size.
2. Owner decision (board question): get a code-signing certificate, sign the installer, and have the updater verify the signature publisher before running it.
3. Owner action (not code): turn on two-factor sign-in and a hardware key for the GitHub account; keep release tokens out of this PC's disk where possible. Branch protection and required review do not apply to a one-person repo, so this is the control.
4. Optional: publish the SHA-512 in a place a second account controls, so a single takeover is not enough.

## S-3 MEDIUM — secrets protected from other users, not from other programs

**Evidence.** `secretStore.js:61,81` call `ProtectedData.Protect/Unprotect(..., $null, 'CurrentUser')` with no optional entropy. Any process running as the owner can run the same two calls on a copied `.secret` file and read every provider key and sign-in token. The agent tools (shell, process start, MCP programs) run as that same user. A prompt-injected agent could be steered to decrypt and send the files. Files are written with `mode: 0o600`, which does nothing on Windows.

**Impact.** DPAPI is the right level against a stolen file or another account; it is not a defence against code the owner (or the agent) runs. Not a defect in the store; the open question is the agent.

**Recommendations.**
1. Builder: add a per-install entropy value (kept in the app's memory/main process only, or stored separately) so that a bare Unprotect fails. Weak but raises the bar for generic stealers.
2. Builder: make agent file and command tools refuse paths under `<dataDir>/secrets` and the data folder's `account.json`; test it. Not run: I did not check how `workspace.folder` and the command runner bound the paths, so this one is UNKNOWN for the agent tools and needs a read of `src/server/agentTools.js` and `workspace` code (follow-up row).
3. Keep DPAPI; do not move keys into settings or plain JSON.

## S-4 MEDIUM — 300 MB import held in memory on an unauthenticated route

**Evidence.** `MAX_IMPORT = 300 * 1024 * 1024` (`app.js:79`). `readBody` (`:108-132`) collects every chunk, `Buffer.concat`, then `toString('utf8')`, then `JSON.parse`, so peak use is several times the file size (chunks + concat + string + parsed object), likely above 1 GB for a full-size body. `parseImport` then works on the string again. The handler runs in the Electron main process that also holds the secrets and the window.
**Impact.** A single request (made by the owner or, through S-1, by a web page) can exhaust memory and kill the app; it is a local denial of service, with no data loss expected. The limit applies to `/api/import` only; other routes keep 1 MB (`:78`), memory import 2 MB.
**Recommendations.** Fix S-1 first. Then: stream-parse or cap at a lower figure (50 MB) with a clear message; refuse `Content-Length` over the cap before reading; reject early rather than reading and dropping the rest (`:115-117`).

## S-5 LOW — text from a model or a pasted file becomes a chat message or a memory

- `move_to_new_chat` (`app.js:2059-2073`): sends `{title, message}` to the window as a new chat. When the setting is `unrelatedTask === 'new'` there is no prompt (`:2065`). The message came from the model, so a page or file the agent read could make it start a chat with text of the attacker's choosing. Impact is bounded: it is a user-visible new chat in the same app, and helper agents are blocked from it (`:1738`). *UNKNOWN: whether the window auto-sends the message; not traced in `src/ui/chat.js`.* Recommendation: show the proposed message and require a click in the "new" mode too, or confirm that the UI only pre-fills it.
- Memory import (`:771-784`): up to 150 lines of 400 characters become standing memories (`source: 'import'`), which are later added to prompts. An imported file can plant instructions that persist. Impact: persistent prompt injection from a file the owner chose to import. Recommendation: show the lines for confirmation before saving (the UI may already; not checked), and mark `source: import` in the list so it can be reviewed.

## S-6 LOW — secret store script construction

`get()` (`secretStore.js:80`) builds `'${cipher}'` from the JSON in the secret file without checking it is base64. A file written by another local program could carry a quote and run PowerShell as the owner when a key is read. Needs write access to the owner's data folder, which already equals the owner's rights, so low. `PS = 'powershell.exe'` (`:15`) is looked up through PATH; use the full path under `%SystemRoot%\System32\WindowsPowerShell\v1.0\`. Recommendation: validate `cipher` with `/^[A-Za-z0-9+/=]+$/` and pin the executable path.

## S-7 LOW — updater file handling

The verified installer sits in `%TEMP%\bunny-ai-update\<name>` (`updater.js:50,59`), a folder any program the owner runs can write to, and `spawn` runs it later (`:122`) without re-hashing. A program with that access could swap the file between the check and the click. `release.name` comes from the release's asset list; GitHub names carry no path separators, but with `BUNNY_UPDATE_FEED` set it is unchecked. Recommendation: download into a per-user folder under `%LOCALAPPDATA%\BunnyAI\updates`, re-hash just before `spawn`, and take `basename(release.name)`.

## S-8 LOW — the 6 moderate `npm audit` findings

`npm audit` (run 2026-11-16): 6 moderate, 0 high, 0 critical — `minimatch` (denial of service through glob amplification, GHSA-based; range 7.0.0 to 11.0.0) and five electron-builder packages that depend on it: `@electron/universal`, `app-builder-lib`, `dmg-builder`, `electron-builder`, `electron-builder-squirrel-windows`.
- All are `devDependencies` used when building the installer; none ships in the app (`package.json:22-24`, `build.files` lists only `electron/**`, `src/**`, `package.json`, icons). The risk is a malicious glob pattern on the build machine, which is the owner's own PC with the repo's own config.
- npm's suggested fix is `electron-builder@25.1.0`, a major *downgrade* of the installed `^26.18.0`: do not apply it. Wait for a newer 26.x that moves its `minimatch`.
- The gate runs `npm audit --audit-level=high` (`scripts/gate.mjs:58`), so moderates never fail it. Recommendation: keep that threshold, record the 6 as accepted until electron-builder moves, re-check on each release.
- One install script is not approved: `electron-winstaller@5.4.0` (`select-7z-arch.js`), flagged by npm during `npm ci`; part of electron-builder's tree; review when updating.

## S-9 INFO — profile photo route

`/api/profile/photo` (`app.js:585-611`): type must match `data:image/(png|jpeg|webp);base64,...` (SVG excluded, good), 15 MB body cap, 10 MB decoded cap, a fixed file `profile-photo` (no user-chosen path), mime saved from the allow-list. Small notes: the bytes are not decoded to confirm they are an image, and GET sends no `X-Content-Type-Options: nosniff`. Add both if convenient. Exposure through S-1 is a photo overwrite; low.

## S-10 INFO — chat search tool

`search_chats` (`app.js:2042-2058`) is a read-only query over this person's own sessions, limited to 8 rows and 240-character snippets, excluding the current chat; the `CHAT_SEARCH_TOOL_RISK` entry marks it `read` (`agentTools.js:215`). It does let text from old chats reach the model, so a poisoned past chat can inject; same class as S-5. No action beyond S-5. It can be switched off (`settings.searchChats === false`, `:1586`).
