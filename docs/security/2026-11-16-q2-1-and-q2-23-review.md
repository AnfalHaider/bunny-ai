## Q2-1: what holds
- The server refuses edit, run and build risks in Plan mode in both dispatchers: the agent tools (`runAgentTool`, `app.js:1949`) and the workspace, app and connector tools (`app.js:2243`). Risk tables cover GitHub and Google tools (merged into `AGENT_TOOL_RISK`, `app.js:62`).
- **Helper agents** (`run_subagent`, `start_session`): `runHelper` creates the child with the parent's `permissionMode` and runs it through the same `runTool` closure, so the same refusal applies; their tool list is filtered from the parent's, which in Plan mode is read-only.
- **Custom tools**: any tool not an agent tool is treated as `run`, so refused. `create_tool` is `build`, refused.
- **Scheduled tasks**: `schedule_task` is `edit` (`build` if it may change things), refused in Plan mode; a schedule created earlier runs with its own mode (`plan` unless set to `auto`, `app.js:373`) and was approved when made.
- **Connector tools** that declare themselves not read-only: `run`, refused.

## Q2-1: bypasses
**Q2-S1 MEDIUM-HIGH. Browser tools skip the Plan check.** `runTool` handles `browserControl && isBrowserTool(name)` (`app.js:2208-2211`) before either dispatcher and checks only `needsOk(...)`, which is false in Plan mode. `browser_click` and `browser_type` (risk `edit`, `browserTools.js:16`) are not offered in Plan mode (`app.js:1623`), but the server does not check that, so a call for them runs: it clicks and types in the in-app browser, where the person may be signed in. This is the exact "tool the model was never offered" case Q2-1 says it closes. Fix: `if (planRefuses(BROWSER_TOOL_RISK[name])) …` in that branch, with a test that calls `browser_click` in Plan mode.

**Q2-S2 MEDIUM. `move_to_new_chat` leaves Plan mode.** Its risk is `own`, so it is not refused. The page then opens a new chat and sends the model's message by itself (`chat.js:2077-2090`, `openNewChatWith`), in the new chat's own mode (the person's default, which may allow edits). With the "unrelated tasks → new chat" setting the server skips the question (`app.js:2065`). So text a Plan-mode chat read in a file can start work in a chat that is not read-only, without a click. Fix: refuse it in Plan mode, or make the new chat start in Plan mode, or fill the message in without sending.

**Q2-S3 LOW. Connector `readOnly` is the connector's own claim** (`app.js:2242`). A connector that labels a writing tool read-only is run in Plan mode. Same trust boundary as adding the connector; note for the connector threat note.

Also noted, no action: `create_artifact`/`update_artifact`/`request_capability` are `own` and allowed in Plan mode by design (own storage; capabilities ask the person).

## Q2-23: token re-read — PASS
`token.js` re-fetches `location.pathname + location.search` with `nativeFetch`, only after a 403 with code `request.noToken` from an `/api/` call of its own origin, reads the new `<meta>` token and retries once.
- A foreign page cannot obtain the token this way: the re-read runs only in Bunny's own page, its fetches go to its own origin, and `isApi` is false for any other origin. A foreign page cannot load `token.js` or the page into itself: those GETs cross-site are refused by the S-1 guard (Sec-Fetch-Site and Host rules; checked on `/` against `ca01243` and `09b35e4`).
- Sandboxed artifact frames have an opaque origin and no token script; their requests are cross-site and refused.
- The retry fires only on `request.noToken`, which the server sends before running the route, so a retried POST cannot run twice.
- `refreshing` joins concurrent refreshes; a failed refresh shows a Reload banner and returns the original 403.
- `sw.js` now ignores other origins; that cannot widen API access.
Not run: no browser test of the restart path (their e2e `request-guard.spec.js` has 19 new lines for it; I did not run them).
