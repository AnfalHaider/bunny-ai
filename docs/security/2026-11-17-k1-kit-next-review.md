## Blockers
**K1-1 MEDIUM-LOW (verified): A3 is not closed for `bootstrap role`.** `role()` (`bootstrap.mjs:151`) has no `plainId` and no check that the id is a known role. In a throwaway repo an unassigned session ran `bootstrap role ../../AGENTS` and `bootstrap role ../../docs/a`: both **accepted**, the role file now says `../../docs/a` and `currentRole` returns it. `loadRole` then reads `.bootstrap/roles/../../docs/a.md` as the role's brief, so a session can pick a brief it wrote itself (`write_globs: ['**']`, no `deny_commands`). Reaching it needs an unassigned session or a route round the guard's "a session that has a role does not change it" rule, so it is not an everyday exposure, but it is the same class as A3 and the README says A3 is closed. **Fix:** `plainId(id, 'role')` and `existsSync(.bootstrap/roles/<id>.md)` after it, in `role()`; add `role ../../x` to test A3. Also let `plainId` refuse a trailing dot and the Windows reserved names (`con`, `aux`, `nul`, `com1`…): today `signoff x.` and `signoff con` run and create `docs/signoffs/x./` and `docs/signoffs/con/` (inside the record folder, so harmless, but `x.` and `x` are one folder on Windows).
**K1-2 MEDIUM-LOW (unknown in the real app; verified in the harness): B7 holds only if the hook process itself runs in the project folder.** `decide()` finds the outer policy through `repoRoot(process.cwd())` (`guard.mjs:94`). With the hook's own cwd set to the project, all six nested-repository attacks were REFUSED (push, `git -C ../..`, redirect and Write into the outer `.bootstrap/` and `AGENTS.md`); with the hook's cwd inside the nested repository (what you get if Claude Code starts the hook in the shell's current folder after a `cd`), **all were ALLOWED**. I do not know which one Claude Code does. **Fix (cheap, no assumption):** walk up from `cwd` and from `CLAUDE_PROJECT_DIR` through every ancestor and use the first folder that has `.bootstrap/policy.json`; keep today's code as the fallback. Or show, with a hook that logs `process.cwd()` after a `cd` into a nested repository, that the hook runs in the project folder, and write that down.

**Accepted, with reasons (none is worse than the v0.1.7 guard that already shipped; the same lists against `scripts/guard-next` give the same or more mismatches):**
1. **#9 the plugin's own hook** runs 0.6.0's regex guard beside ours. It can only add refusals; the false blocks I have seen all week come from it. Accept; note that `bootstrap upgrade` reads the plugin's `bin/`, so **running `/upgrade` after landing would copy the plugin's plain 0.6.0 guard over ours**. The push check should stop it (it changes `.bootstrap/bin/**`, so Security's sign-off is required), but nobody should run `bootstrap upgrade` until the plugin carries our patches. Put that line in `AGENTS.md`.
2. **B1 interpreter one-liners** (`node -e`, `python -c`, `[IO.File]::WriteAllText`, `Start-Process powershell -ArgumentList '…'`), **and the other routes that run arbitrary code** (`icacls`, `attrib`, `robocopy /MIR`, `git clean -fdx`, `git update-index --assume-unchanged`): the guard reads commands, it is not a sandbox. The pre-commit and pre-push hooks are the backstop; they judge by the role, and the role can be changed by the same arbitrary code. Accept as the standing limit (the same as W5-1), but say it plainly in the README.
3. **Hard link or symbolic link to the role file** (`cmd /c mklink /H x .git\bootstrap-role`, `fsutil hardlink create`, `New-Item -ItemType HardLink|SymbolicLink`, `ln`, `cp -l`): ALLOWED by the guard; writing through the link changes the role. Same class as item 2 (arbitrary code already does it), so accept. A cheap tightening that makes it tamper-evident: `currentRole` ignores a role file whose link count is above 1 and refuses the link-making commands that name the role file.
4. `refs/heads/Main` and other case variants of the live branch can be pushed: GitHub treats `Main` as a different branch, nothing publishes from it. Accept.
5. **Quoted-argument wrappers for pushes:** `powershell -c "git push origin main"`, `bash -c '…'`, `sh -c '…'`, `iex '…'`, `Invoke-Expression "…"`, `Start-Process git -ArgumentList 'push origin main'` and the half-quoted `git p"ush" origin main` are ALLOWED by the shell layer (identical on v0.1.7; `cmd /c git push …` and `powershell -Command git push …` are refused). For a non-live role the pre-push hook (role-based) still refuses `main` and tags; for a live role the push is allowed anyway. Follow-up (K1-4): read the quoted argument of `-c`/`-Command`/`-e`/`iex` with the same tokenizer.
6. **K1-3 LOW:** the Write tool is not told that a UNC path to the same folder (`\\localhost\C$\…\.bootstrap\policy.json`, `\\127.0.0.1\C$\…`, `\\?\UNC\localhost\C$\…`) is the protected file: ALLOWED. On this machine the admin share is not reachable (`Test-Path \\localhost\C$\Users` is False), so I could not make it write; where admin shares are on, it would. The shell layer refuses the same spellings. Fix: treat any UNC path as "outside, refuse" for file tools, or map a loopback UNC to its drive path. Same on v0.1.7.
7. `git commit-msg`: a trailer indented with a space or tab is not matched (the pattern is anchored at the line start); git does not read an indented line as a trailer, so GitHub should not credit it. The `noreply@anthropic.com` pattern is not anchored and catches the email in any case. Accept.
8. `plugin_hook` / `legacy_deny_all` / helper-agent limits: read, no change from 0.6.0 where I looked.
