## W6-13 — `download_file(url, path)` — FAIL (W613-1)
**What holds.**
- **Where it writes:** the same gate as `write_file` (`inside()`, junction and `..` safe): `../x`, `..\x`, an absolute path, `C:/…`, `/x` are refused; Plan mode refuses it (risk `edit`); an undo checkpoint is taken before the write.
- **Addresses:** http or https only (`file:`, `ftp:`, `gopher:`, `data:`, `javascript:` and an empty URL refused, also as a redirect target). A literal address is parsed, so `2130706433`, `0x7f.1`, `017700000001`, `0` and `localhost.` are all refused as 127.0.0.1 / 0.0.0.0. 33 spellings of private addresses checked through `isPrivateAddress` (loopback, 10/8, 172.16/12, 192.168/16, link-local 169.254.169.254, 100.64/10 and 100.100.100.200, 0/8, multicast, broadcast, `::1`, `::`, IPv4-mapped and IPv4-compatible in both dotted and hex forms, NAT64 and 6to4 embedding a private address, `fc00::/7`, `fe80::/10`, `ff00::/8`, a zone id, brackets, garbage): all refused except one (below); 12 public addresses (including the edges 100.63.x, 100.128.x, 172.15.x, 172.32.x) are not over-refused.
- **DNS:** the name is resolved **once**, every returned address must be public (a name that returns one public and one private address is refused), and the socket is given exactly the validated address, so a rebind between check and connect cannot swap it; TLS still uses the host name.
- **Redirects:** at most 5, each hop goes through the same literal and DNS check (read; I cannot stand up a public server here), `file:` as a target refused, a redirect loop stops at 5.
- **Size and time:** 50 MB, checked on the declared length and again while streaming (a declared 60 MB and a chunked 60 MB are both refused with nothing saved); 60 s in all; no cookies or auth sent; response headers are not echoed back.
- `allowLoopback` is a test switch and turns **all** address checks off, not only loopback; the app never passes it (`createWorkspace` is called without it in `app.js`; its default reads an environment variable that only tests set). Rename it before anyone reuses it.

**W613-1 MEDIUM (verified): the person's path rules do not apply to it.** `permissionRules.EDIT_TOOLS` is `write_file`, `edit_file`, `multi_edit`. With a Deny-edit rule on `secrets/**`, the rules engine answers `deny` for those three and **nothing for `download_file`**. So where the rules matter (Accept edits and Auto; Manual asks anyway) a model can overwrite `.env` or anything under `secrets/` with whatever an address returns. Allow and Ask path rules do not see it either. **Fix:** add `download_file` to `EDIT_TOOLS` (its path is `args.path`), and add it to the rule test.
**W613-2 LOW:** the address `::ffff:0:127.0.0.1` (IPv4-translated, a different prefix from IPv4-mapped) is treated as public. A normal Windows host does not route it. Add `::ffff:0:0/96` to the blocked ranges.
**Same class as the existing edit tools, not new here (see W6-NEW-1 below):** `download_file` will write `.git/hooks/pre-commit`, `AGENTS.md` and an NTFS stream (`x::$DATA`).
**Note:** a `GET` with a secret in the address is a way to send data out; `read_url` and `web_search` already are, so nothing new, but it is why `download_file` must not run silently where the person has told the rules to hold.

## W6-9 — `file://` in `read_url`, folder listing in `read_file` — FAIL (W69-1)
**What holds (15 spellings through the real workspace):** `file://` of a path inside the workspace reads it; outside the folder, `..`, `%2e%2e`, a junction that leads out, a remote host (`file://evil.example/share/x`), a drive root and a trailing-dot name are all refused with "can only read files inside the workspace folder"; a folder lists its entries (200 lines); Chat mode (no folder) refuses. It goes through the same `inside()` gate as `read_file`.
**W69-1 MEDIUM (verified): read Deny rules do not apply to it.** The rule check in the runner is `const ruled = isWorkspace ? checkToolCall(...) : null`, and `read_url` is an app tool, so a `file:` address goes to `readFileUrlIn` with **no** rule check: with `Deny reads` on `.env` and `secrets/**`, `read_url file:///<workspace>/.env` returned `ENV-SECRET` (also upper-case `.ENV`) and `…/secrets/k.txt` returned `KEY-SECRET`; the rules engine answers "no rule" for the `read_url` call. (The `hidden` filter only hides names in listings and searches; `read_file` itself relies on the rule check in the runner.) **Fix:** in the runner, for `read_url` with a `file:` address, resolve the path and run `checkToolCall(rules, 'read_file', { path }, canon)` before reading, and refuse with the same "Blocked by your permission rule" message; add the case to the rules test.

## W6-21 — tool results up to 50,000 characters — PASS
- A tool result now reaches the model up to 50,000 characters (`fitResult`; the middle is cut with a note saying how to read the rest), general tools up to 30,000, command output keeps 50,000. That is for the model that asked; nothing here widens who sees it.
- **What is kept stays gated by the W6-18 rules.** The stored longer copy (`modelResult`, 8,000) and the `.bunny/notes` file are still made only for workspace tools, never when the result looks secret (`looksSecret`, which fails closed above 128 KB), never in an incognito chat, never in Plan mode; the chat shows the first 1,200 characters; a model that takes over replays 8,000 per step (60,000 in all). I re-read the diff for a path that stores the bigger text: `fullResult` is cut at 2,000,000 characters and goes only into that same gate.
- LOW notes: (1) for a result over 128 KB the model is told "the whole output is saved in `.bunny/notes`", but the secret check treats anything that large as unsafe and does not save it, so the sentence is wrong for the biggest outputs; say "not saved" or save after a size-limited scan; (2) the live conversation now carries up to 50,000 characters per step, which the provider receives every round (cost, not secrecy; `shrinkConversation` still trims older ones).

## New finding that touches all the edit tools (W6-NEW-1, MEDIUM-LOW, pre-existing)
`write_file`, `edit_file`, `multi_edit` and now `download_file` will write inside `.git/` (I wrote `.git/hooks/pre-commit` with `write_file` in a throwaway repository: allowed). A hook written there runs the next time the person commits. In Manual mode the person sees the path; in Accept edits and Auto it runs unasked. The panes already refuse `.git` for reading (D2-4). **Fix:** refuse a path whose real location is under the repository's `.git` folder in all four edit tools unless the person's own rule allows it, and say so in the refusal.
