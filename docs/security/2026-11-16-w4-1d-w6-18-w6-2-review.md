## W4-1d — detached supervisor for started programs: **PASS** (one functional bug to fix)

**Can it be abused to kill other processes? No.** `procGuard.js` is started only by `processes.js` with the server's own pid and the command as one JSON argument. It kills one thing: `taskkill /pid <its own child> /T /F` (Windows) or its own group (POSIX). It never kills the server pid it watches. Anything that can start `procGuard.js` by hand can already run any command, so it adds no reach.
**Does it leak itself? No.** It exits when its child exits, and when the server's pid is gone it kills the child's tree and exits. In my probe, `stopAll()` left no supervisor alive, and Builder's test (kill the stand-in server, check the program is gone) passes.
**Arguments.** The command reaches PowerShell as the same text as before, inside one JSON argument that Node quotes for Windows; nothing new is parsed as a command line.

Follow-ups:
- **W41d-1 LOW-MEDIUM (verified):** `ELECTRON_RUN_AS_NODE=1` is set for the supervisor and then inherited by the started program: `node prog.js` printed `ERN=1`. Any Electron program the model starts (`npm start` in an Electron project, `code`, another Bunny) will run as plain Node and fail. Fix: give the child an environment without that variable (`const { ELECTRON_RUN_AS_NODE: _, ...env } = process.env` in `procGuard.js`).
- **W41d-2 LOW:** `alive(serverPid)` is a bare pid test. If the server dies and its pid is reused, the supervisor never fires and the program lives on; and `EPERM` counts as alive. Windows reuses pids slowly, so this is rare. Fix (optional): also compare the process start time, or have the server hold a pipe open to the supervisor (its death closes the pipe at once, no polling, no pid reuse).
- Not tested: a packaged app (the supervisor runs `Bunny-AI.exe` with `ELECTRON_RUN_AS_NODE` on a script inside `app.asar`; `package.json` includes `src/**`, so the file ships). Grandchildren whose parent has already died are not in the tree and are not stopped (same as before).

## W6-18 — whole results kept for a takeover; big ones saved in `.bunny/notes/`: **PASS with conditions**

**Held (read and tested):** notes are written only for workspace tools (`saveable: isWorkspace`, line 2437) and only when the result is over 6,000 characters; never in Plan mode; `.bunny` and `.bunny/notes` are `lstat`ed and refused if they are a link or a file, and the real path of `notes` must stay inside the real workspace; `.bunny/.gitignore` (`*`) is written once; the file name is made by the server (`step-<time>-<n>.txt`), and the stored `resultFile` must match `^\.bunny/notes/[\w.-]+$` (so a poisoned chat file cannot point the model elsewhere); screenshot replay accepts only `/api/screens/<uuid>.png`. Tests cover the Plan-mode and linked-folder cases.

**Builder's "workspace tools only" is true for the notes files, not for the stored copy:**
- **W618-1 MEDIUM-LOW (code reading, lines 1618-1624, 2337, 2393):** `keepForModel` runs for every tool step, and the general tool path (line 2337: Gmail, Drive, Calendar, GitHub, memory, connectors, custom tools) and the browser path (line 2393) pass `fullResult`. So up to 6,000 characters of an email, a Drive file, a web page or a connector's answer are stored in the chat file as `modelResult` (cap 8,000 in `sessions.js`) and replayed to whichever model takes over, which can be a different provider after a failure. Before this change a step kept 300 characters. Fix: only steps with `saveable` (workspace tools) get `modelResult`; others keep the short result as before. Add a test that a mail or connector result stays at 300 characters.
- **W618-2 LOW-MEDIUM, secrets in notes:** a `read_file` of `.env` or a `run_command` that prints tokens (`git remote -v` with a token URL, `npm config list`, `printenv`) over 6,000 characters is saved as plain text in the person's project folder, never deleted, also in a private (incognito) chat. `.gitignore` keeps it out of `git add`; it does not keep it out of a zip, a folder share, a cloud-synced folder, or the model's next `read_file`. Path rules on `.bunny/**` do not apply to Bunny's own writes. Fix: (a) a size and age limit (keep the newest 50 notes or 7 days, delete the rest at the start of a Code chat), (b) do not save when the chat is incognito, (c) do not save when the result matches a secret pattern (private key block, `Authorization:`, `sk-`/`ghp_`/`AKIA`-style tokens, `password=`), keeping only the clipped text, (d) say in the Code settings help that notes live in `.bunny/notes` and can be deleted.
- **W618-3 LOW:** the link check and the write are separate steps: a background program started by the model (`start_process`) could swap `.bunny/notes` for a junction between the `lstat` and `writeFile`, so a text file named `step-…txt` with tool output lands in the target folder. The file name and `.txt` ending are fixed, so this is a nuisance write, not code. Fix (optional): open the file with a flag that refuses links, or write to a temp name and rename inside the checked folder.

## W6-2 — auto-continue up to 500 steps or 2 hours: **PASS with conditions**

**Stop holds.** `extendRounds` is not asked once `signal.aborted` is set (line 71, tested); an aborted round returns at once (line 86) and the fetch itself carries the signal. **Asks and sends hold.** Nothing in the change touches `needsOk`, rules or Plan mode: every tool call still goes through the same `runTool`, so every ask, every email send and every Plan refusal happens at step 400 as at step 4. Extra steps only happen in Code mode or with a workspace (line 2467). The sub-agent loop does not get `extendRounds`.
**Can injected text keep it running?** Yes, up to the cap: the model decides to call the next tool, and nothing but the cap, Stop or a Deny stops a loop. In Manual and Accept edits each edit or command still waits for the person, so a poisoned page cannot run unattended there. In Auto it can run up to 500 steps or 2 hours with no question, where it used to stop at the step budget of the effort setting (a few rounds). Deny rules, Plan, the "still ask" for building a tool, a local connector and a change-making schedule, and email send all still hold in Auto.

- **W62-1 MEDIUM, cost has no cap (money):** 500 steps each resend a conversation of up to 240,000 characters (about 60,000 tokens) to a paid provider, so one runaway reply can spend tens of millions of input tokens (500 × 60,000 = 30 million). The only brakes are steps, time, and Stop. Fix: a default that costs a person little (for example 100 steps), a visible running step count and elapsed time next to Stop (the "Still working · step N" line is the start), a loop check (the same tool and arguments three times in a row, or no new file changed in 30 steps, ends the run with a report), and in Settings show the cap as "up to N steps, about X million tokens".
- **W62-2 LOW-MEDIUM, the caps can be raised by anyone with the page token:** `autoContinueSteps` and `autoContinueMinutes` (no screen for the minutes) are plain settings, written by `PUT /api/settings` (token only; the W2-7 window-only list does not include them), and read with no upper limit (`Number(...) || 0`). A model with `run_command` in Auto, or any local program, can set 1e9 steps. Fix: clamp both on read (for example 1,000 steps, 8 hours) and add the two keys to `WINDOW_ONLY_SETTING_KEYS` once W2-7 is in.
- **W62-3 LOW, Auto and scheduled runs:** a scheduled task with `may_change` runs in Auto, and now each run may continue for 2 hours. Pair with W62-1: lower default for Auto and for scheduled runs (for example 100 steps and 30 minutes).

## Not done
No gate or e2e; no real model driving 500 steps; no packaged app; W4-1d's pid-reuse case was not provoked; W6-18's link race not provoked; the cost figure is arithmetic from the constants in the code (240,000 characters, 4 characters a token), not a measured bill.
