## W4-8 quick-ask bar — **PASS**

**It never captures the screen unasked.** `desktopCapturer.getSources` is called in exactly one place, `capture()` in `quick-ask.js:98` (a repo-wide search finds no other call), and `capture()` runs only from the IPC `quickask:capture`. That IPC answers only the bar itself: the sender must be the bar's own `webContents` **and** the frame URL must be the local `quick-ask/bar.html`; anything else, including Bunny's main window, gets "Not allowed". The bar's script calls it from one place: the click on "Add a screenshot", which sits behind the "+" menu (two deliberate clicks). The shortcut and the bar opening do not capture. One picture only (the list is limited to one and must be a real PNG: signature checked, 8 MB cap, shrunk if larger), shown as a chip with an × that removes it, and the bar hides itself for the capture so it is not in the picture.
**It is kept only where the owner said.** The picture lives in the bar page's memory until the message is sent; Escape or a successful send destroys the bar (and the text); clicking away hides the bar and destroys it after 5 minutes. On send it goes into the first message of a new chat as an ordinary image attachment, and nowhere else.
**The bar is a closed box.** `contextIsolation`, `sandbox`, no Node, `webSecurity`, a page CSP of `default-src 'none'; script-src 'self'; img-src data:`, no navigation, no redirect, no new windows, no webviews, every permission request refused. Its bridge has two functions (`submit`, `captureScreenshot`). Its text goes in only with `textContent`/`.value`. The message is validated again in the main process (type, 20,000 characters, one PNG).
**What it starts is small.** A new chat in **Chat mode with no folder and no project** (no tools), and a message that begins with `/` gets an invisible word joiner so it cannot run as a slash command; if Bunny is already answering, the request is refused with a message instead of interrupting. `quickask:take` hands the request to Bunny's own window once (own-page check) and clears it.
**Window-only keys.** With only the page token: `PUT /api/settings` of `quickAskEnabled` and of `quickAskShortcut` answer **403** `request.windowOnly` (the list was extended in `e061ce6`, with the page's copy in `api.js`; the equality test passes). The two preferences actually live in the desktop preferences file behind the window's own `prefs:set` bridge, which no HTTP request can reach.
**Shortcut and window cannot be driven by another program through any channel of ours.** The only way in is the operating system: a program that can press the global shortcut and type is typing into the bar like a person. What it can then do is send one message to a **new Chat-mode chat** (no tools) or choose "Add a screenshot" with synthesised clicks; anything that can synthesise input can already do both in Bunny's main window, and the shortcut is **off by default**, needs Ctrl, Alt or Win, and is unregistered when switched off.
**Notes (LOW):** (1) the screenshot goes to whatever model the new chat uses, as any attachment does; the "+" menu says it takes a picture of the screen when chosen; (2) text typed in the bar stays in memory for 5 minutes after a click-away (by design, so a slip is not lost); (3) the bar is always-on-top at the "screen-saver" level, so it also appears over full-screen apps, as intended for this feature.

## W4-10 plugin install and uninstall — **PASS**

**The routes are closed.** With only the page token, in the desktop-app configuration: `POST /api/plugins` (a catalog entry and a file body), `DELETE /api/plugins/:id` and `POST /api/plugins/install` all answer **403** `request.windowOnly`; `PUT /api/settings` with `plugins` answers 403. (The routes were open before `e061ce6`; Builder B caught it, and the table now has `POST /api/plugins` and `DELETE /api/plugins/<uuid>`.)
**Uninstall cannot delete outside the plugin's own parts.** `uninstall(id)` looks the plugin up in the **server's own list** (`settings.plugins`, window-only), and removes exactly the connector and skill ids written down at install: `mcp.remove(id)` and `skills.remove(id)`, nothing else (no file paths, no name matching). Those ids are made at install time: `mcp.add` and `skills.add` always create a new record with a fresh UUID (I read both; neither returns an existing record), so a plugin can never claim, and uninstall never remove, a connector or skill the person had before. An id that is already gone is skipped; an unknown plugin id removes nothing.
**What an install can add.** From the window's catalog or file, a bundle's connectors are reduced to `{name, url}` (a remote address; `mcp.add` refuses anything that is not http or https), so a bundle cannot add a local connector (a program on the PC); its skills are the text it carries. A second install of the same plugin is refused (one plugin, also for two clicks at once: installs and uninstalls run one at a time through a queue); a half install is undone part by part. The model's own `install_plugin` tool (GitHub link) still asks the person, unchanged.
**Notes (LOW):** (1) installed connectors are switched on at once, as before; (2) **when W3-6 (sign-in connectors) lands, `uninstall` must call the same sign-out the connector delete route uses** (`signOutQuietly`): `appTools.uninstall` removes a connector through `mcp.remove` directly, which would leave its stored sign-in token behind; W3-6 is not in this branch, so nothing is wrong today; (3) a bundle has no cap on the number of skills or connectors (the person chose the file or the catalog entry).
